## Что изучается

Все три варианта используют OpenMP для запуска потоков. Название файлов
`no_omp` здесь не означает отсутствия OpenMP: вместо готового `reduction`
частичные суммы вычисляются и объединяются вручную.

1. **`sum_par`, вывод `cyclic`.** Поток с номером `t` складывает элементы
   `t, t + T, t + 2*T, ...`. У каждого потока своя ячейка суммы. Соседние ячейки
   могут находиться в одной строке кеша, вызывая лишние обмены между ядрами
   при записи. Это называют ложным разделением кеша (false sharing).
2. **`sum_loc`, вывод `padded`.** Между ячейками сумм оставлен промежуток:
   используем `partial_sums[t * D]`. При принятом размере строки кеша 64 байта
   разные потоки записывают в разные строки. Элементы массива всё ещё читаются
   с шагом `T`.
3. **`sum_blocks`, вывод `blocks + tree`.** Каждый поток получает непрерывный
   блок и сначала складывает его в локальную переменную `my_sum`.
   Затем частичные суммы объединяются парами, четвёрками, восьмёрками и т. д.
   Между уровнями дерева стоит `barrier`, чтобы все потоки завершили предыдущий
   уровень до чтения его результатов. Условие `t + step < T` позволяет работать
   и с числом потоков, которое не является степенью двойки.

Эти версии показывают последовательность изменений из занятия. В третьей
одновременно изменены чтение массива, накопление суммы и её объединение:
разницу во времени нельзя приписать только одному из этих изменений.
Величина 64 байта — предположение учебного примера, а не правило для всех CPU.

## Исправления исходников

- В первой версии память от `calloc` не освобождалась. Во второй и третьей
  использовался `malloc`, после которого ячейки сумм не были обнулены перед `+=`.
  В рабочей программе `std::make_unique<double[]>(...)` обнуляет массив
  частичных сумм и автоматически освобождает память при выходе из функции.
- В третьей версии `double my_sum;` не имел начального значения.
  Исправлено на `double my_sum = 0.0;`, а запись результата — на
  `partial_sums[t * D] = my_sum;`.
- `omp_get_num_procs()` возвращает число доступных процессоров, которое не
  обязано совпадать с числом потоков. Это могло привести к выходу за границы
  массива сумм при `OMP_NUM_THREADS` больше числа процессоров.
  Для выделения памяти используется `omp_get_max_threads()` перед параллельной
  областью, для раздачи элементов — фактическое `omp_get_num_threads()` внутри неё.
- Комментарий к ожидаемой сумме исправлен: `0x1P+55 - 0x1P+27`
  означает `2^55 - 2^27`, а не `2^56 - 2^27`.
- Разность `omp_get_wtime()` умножается на 1000 для вывода миллисекунд.
- Вместо `%g` суммы выводятся целиком через `%.0f`, а относительные ошибки —
  через `%.6e`, как в первой практике. В исходниках из архива выводилась
  абсолютная разность, поэтому её числа нельзя напрямую сравнивать с относительной ошибкой.

При прямом запуске без аргументов все варианты считают один массив из
`1u << 28` элементов (2 ГиБ). Для этого N ожидаемая сумма — `36028796884746240`.
В переносимой сборке можно передать `--size 1000`; ожидаемая сумма
пересчитывается по `N*(N-1)/2`. F5 использует небольшой массив из 1048576 элементов.
Отличия результатов
из-за округления `double` допустимы, в том числе нулевая ошибка.
Результат одного замера не гарантирует, что следующий вариант всегда быстрее.
